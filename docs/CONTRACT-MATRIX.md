# Host contract coverage matrix

The generated matrix is separate from the engine capability inventory in [CAPABILITIES.md](CAPABILITIES.md). Run [the differential command](CONTRACT-DIFFS.md) to obtain current machine evidence. Reports are generated artifacts, not a replacement for the existing human audit.

The profile input follows the actual installed `dsh-base` and `dsh-web-app` package manifests' `dsh.bundle.patch` declarations, in order. Inserted rows are expanded and id overrides applied, then preset `config.plugins` and nested group configurations are traversed recursively. Every resulting `@deepseek-ai` plugin entry, including conditional, disabled and client rows, enters the family union; their original disabled expressions remain data, never activation evidence. Unrecognized top-level patch operations fail rather than silently narrowing enumeration. This is the shipped profile universe, including conditional rows, not a claim that all plugins activate in one deployment. User custom patches, optional external bundles and expression evaluation are outside this bounded profile input.

The runtime fixture is an explicit subset: llm, session, system-prompt, tools, session-projection, goal, goal-round-driver, tool-todo, tool-goal and agent, plus exactly one loop. It does not boot the full web profile. The machine report associates plugin families with only scenarios whose assertions demonstrated use in both runtimes, and emits `no-scenario` for every other family. A scenario may be triggered yet fail equivalence; consult execution status separately. Compact, subagent/side paths, filesystem, persistence, and other deployed plugin families therefore remain visible gaps.

L1 covers all three registration sets: projection keys (from the registry's public checkpoint over the created session), Cordis service keys (from the installed reflection registry's service discriminator and live `get`, since no public enumeration exists), and registered tool names (public schemas). Each is captured after startup/create and again at scenario completion. All registered projection states are read, including those without client wire views.

L0 mechanically scans the installed stock loop's bundled JavaScript with the TypeScript AST. It records `session.append`, `.register`, `.withInitiator`, `.stateOf`, and `.on` call sites with package version, per-file SHA256, location, call text, category and whitespace-stable content fingerprints plus duplicate occurrence ordinal. Matching zero calls or unavailable sources fails. Broad method matches can include unrelated receivers. Bundled file locations and lexical matches do not establish semantic completeness or reachability.

Every static obligation initially remains **unknown** with an empty scenario-evidence list. The runtime fixture demonstrates end-to-end consumers but does not instrument individual stock call sites; it cannot honestly mark them individually covered. Unknown obligations and families without scenarios count as partial coverage and fail strict mode after an otherwise passing differential. A new/modified call receives a new fingerprint and cannot inherit a covered row automatically.

This evidence cannot prove rewind, checkpoints, file rollback, memory, or the completeness of any engine capability bridge. It provides a repeatable oracle and a traceable list of missing evidence, with honest failures while differences remain unresolved.

Observed differences in the original three scenarios are classified in [CONTRACT-ROOT-CAUSES.md](CONTRACT-ROOT-CAUSES.md), with an immutable [original 289 ledger](CONTRACT-ORIGINAL-289.json). Classification distinguishes actual missing events and registrations from positional amplification; it does not turn unknown static obligations or unexercised profile families into coverage.

The actionable `pnpm verify:contracts` command reuses one fresh matrix capture and adds a source-evidenced semantic gate. Its current PASS is explicitly bounded to the three executed scenarios; the raw comparator still reports FAIL, and family/static coverage is still partial. `--strict-coverage` exits 2 after an otherwise passing semantic gate. Historical 289 membership and current repair status are presented separately in the generated standalone report; no coverage row is promoted by classification.
